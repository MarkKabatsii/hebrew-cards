# Технічне завдання v2 — «Навчальний маршрут»

Дата: 10.10.2026. Проєкт: hebrew-cards. Статус: специфікація для реалізації та перевірки в локальному репозиторії.

Ця редакція повністю замінює попереднє CODEX_LEARNING_PATH_UA.md. Якщо робота вже почалася, зістав наявні зміни з v2 і продовжуй із них; не видаляй реалізацію та не починай переписування автоматично.

## 1. Мета, межі та повноваження

Реалізуй додатковий розділ «Навчальний маршрут»: послідовні рівні до 5 слів, знайомство, письмове пригадування в обох напрямках, відновлення прогресу та коротке повторення. Результат — локально перевірений модуль, SQL-міграція й інструкція запуску.

Стек нового модуля: React + TypeScript strict. Vite використовуй, якщо в репозиторії немає придатного збирача; наявний придатний збирач збережи, щоб не вести дві системи. Next.js не додавай: у цьому завданні немає вимоги серверного рендерингу. Supabase залишається системою авторизації та збереження даних.

Усі нові компоненти й навчальна логіка — .tsx/.ts. Старий JavaScript мігруй лише в мінімальному обсязі, потрібному для інтеграції. Не додавай Redux, окремий backend, універсальну платформу курсів або нову дизайн-систему без конкретної необхідності.

Не входять у завдання: переписування всього застосунку, зміна старого SRS, повноцінна offline-синхронізація, рейтинги, антишахрайська перевірка результатів, AI-оцінювання перекладу, озвучення, редактор усіх навчальних матеріалів, автоматичне схвалення прикладів.

Працюй послідовно до завершення всіх етапів нижче. Рутинні рішення приймай самостійно. Не зупиняйся лише з планом. У разі зовнішнього блокера заверши незалежні частини й точно опиши блокер. Production SQL, push та deploy не виконуй. Не перезаписуй сторонні зміни; не запускай reset/clean або генератор нового проєкту поверх репозиторію.

## 4. Продуктові правила

### 4.1. Склад маршруту

- Маршрут персональний, використовує власні доступні слова поточного користувача. Без жорстко заданих ID власника, кількості 487 чи локального CSV як production-джерела.
- У першій версії один маршрут на всі категорії; фільтри категорій не впливають на його склад. Новий рівень — до 5 слів, ще не завершених у цьому маршруті.
- Порядок кандидатів стабільний: created_at ASC NULLS LAST, id ASC, якщо це відповідає схемі. Якщо ні — задокументуй стабільний еквівалент. Вибір не обмежувати випадково першою сторінкою відповіді API: використовуй пагінацію або серверний вибір кандидатів.
- Не створюй усі майбутні рівні наперед. При старті атомарно зафіксуй склад поточного рівня. Одночасні натискання у двох вкладках повертають той самий активний рівень, а не два різних.
- Додавання слів не змінює активний рівень; вони стають кандидатами наступних. Коли слів немає, показуй «Усі доступні слова опрацьовано»; після додавання нових слів маршрут продовжується.
- Старий SRS не означає автоматичного завершення цього маршруту. Його поля не змінюються.

### 4.2. Режими та навантаження

| Режим | Знайомство на слово | Правильні HE→UK | Правильні UK→HE | Для 5 слів без помилок |
| --- | ---: | ---: | ---: | ---: |
| Звичайний, типовий | 5 | 3 | 3 | 25 переглядів + 30 письмових відповідей |
| Інтенсивний | 10 | 10 | 10 | 50 переглядів + 100 письмових відповідей |

Пороги — продуктова початкова гіпотеза, а не доведений критерій засвоєння. Зберігай mode, thresholds і rules_version при створенні рівня. Зміна налаштувань у новій версії застосунку не змінює активний рівень. Режим можна обрати перед стартом наступного рівня.

Лічильники правильних відповідей накопичуються, не вимагають безпомилкової серії й не обнуляються через помилку. Завершення називай «Опрацьовано в маршруті».

### 4.3. Стабільність навчального матеріалу

При старті рівня збережи snapshot основного матеріалу кожного слова: he, ua, tr, прийняті варіанти відповідей і версію нормалізації. Редагування словника не змінює правильну відповідь посеред активного рівня. Новий сеанс повторення отримує актуальний матеріал. Повідомлення про активний snapshot має бути коротким і зрозумілим лише там, де це потрібно.

Приклади отримуй окремо з актуальних approved-записів; не зберігай їх навічно в snapshot, щоб відкликаний приклад не повертався з історії. Використовуй поточну захищену вибірку без запиту на кожну картку; відсутність прикладів не блокує навчання.

При видаленні слова або втраті доступу до нього виключай його з подальших вправ при відновленні та перед підтвердженням наступної дії. Не відновлюй видалене слово зі snapshot. Вибери й задокументуй FK/tombstone-поведінку, що зберігає цілісність і не дозволяє повторно показати видалений контент.

Виключене слово не замінюється новим у поточному рівні, не отримує балів і не вважається опрацьованим. Решта слів завершують рівень; якщо не лишилося жодного — статус cancelled_empty, а не успішне завершення. Жоден випадок не повинен блокувати початок наступного рівня.

## 5. Модель стану і моменти зарахування

Зроби явні типи phase = introduction | he_to_uk | uk_to_he; status = active | completed | cancelled_empty; стан вправи = question | feedback. Окремо тримай тимчасовий UI-стан: введений текст, фокус, saving/error, відкритий зворот.

Не використовуй незалежні прапорці, що дозволяють одночасно completed і active або feedback без результату. Представляй взаємовиключні варіанти discriminated unions. Зберігай schema_version; невідому новішу версію не скидай в порожній прогрес.

| Дія | Передумова | Зміна підтвердженого стану |
| --- | --- | --- |
| Відкрити зворот | introduction/question | Лише UI, без балів і запиту збереження |
| Далі у знайомстві | Зворот був відкритий | Один перегляд + перехід до наступної вправи в одній транзакції |
| Перевірити відповідь | Письмова question, непорожній текст | Результат + можливий бал; та сама вправа переходить у feedback |
| Не знаю | Письмова question | Результат revealed, 0 балів; feedback |
| Далі після перевірки | feedback уже збережений | Наступна вправа, етап або завершення; без повторного бала |

На останній правильній відповіді спочатку залишається feedback. Рівень завершується при «Далі» після цього feedback; перехід і завершення атомарні. Втрата відповіді сервера або подвійний клік не завершують рівень двічі.

Зберігай exercise_id, поточне слово, напрямок, чергу, позицію, лічильники, останній збережений feedback. Після reload відновлюється останній підтверджений стан: question або feedback. Незавершений набір тексту і незарахований перегляд звороту після reload можна втратити; не обіцяй їх збереження. Якщо запит був підтверджений сервером, але відповідь не дійшла, серверний стан визначає результат після reload.

## 6. Черга й інтерфейс вправ

Знайомство: слова по колу у стабільному порядку, завершені за порогом виключаються. На звороті — tr, ua та до двох approved-прикладів у порядку example_order.

Письмові етапи: кожне незавершене слово один раз за цикл; новий цикл перемішаний. Не став те саме слово підряд, якщо є інше незавершене. Якщо залишилося одне — повтор допускається. Після помилки слово повертається в наступному циклі.

Порядок циклу зберігається або детерміновано відновлюється зі збереженого seed/номера циклу. Не запускай Math.random під час render, відновлення або чистого reducer. Переходи до наступного етапу дозволені лише після досягнення порога всіма невиключеними словами.

HE→UK: слово івритом і поле українською. UK→HE: значення українською й поле івритом. Переклад/відповідь, транскрипція й приклади до перевірки не рендеряться у доступному DOM вправи. Не покладайся лише на opacity, transform або прихований зворот картки.

Після перевірки — результат, очікуваний варіант, приклади та «Далі». Для уникнення пастки невідомого слова є «Не знаю» без бала. Поле та повторна перевірка блокуються до наступної вправи. Не прив’язуй введення пробілу у полі до перевороту; обробляй Enter через submit форми та враховуй IME/composition.

## 7. Перевірка перекладу: чесні межі

Чисті функції normalizeUk, normalizeHe, evaluateAnswer мають конкретні fixture-тести. Порівняння — рівність нормалізованій допустимій відповіді, не includes і не довільне приблизне співпадіння.

Українська: Unicode-нормалізація, trim, згортання пробілів, регістр, наголос U+0301, поширені варіанти апострофа. Не видаляй усі combining marks: після декомпозиції це може зруйнувати й/ї. Не прирівнюй і/и, г/ґ, е/є.

Іврит: ігноруй нікуд і кантиляцію лише в явно визначених діапазонах, а не весь блок Hebrew Unicode. Не видаляй літери, не прирівнюй фінальні форми до звичайних, не зводь різні написання до одного без explicit alias. Зафіксуй правила для maqaf, geresh/gershayim та крапок у скороченнях і перевір їх. Обмеж довжину введення розумним документованим лімітом.

Гнучкі синоніми потребують даних. У першій версії підтримай answer variants для обох напрямків, прив’язані до word_id і власника, з документованим способом наповнення. За відсутності варіантів приймай точне нормалізоване основне поле. У знайомстві показуй допустимі відповіді, якщо вони відрізняються від повного словникового опису.

Не розбивай автоматично ua за комами/слешами; не оголошуй довільний синонім неправильним за змістом: текст помилки «Відповідь не збігається з варіантами словника». Для багатозначних/складених записів підготуй перелік матеріалів, де потрібні короткі погоджені варіанти. Не вигадуй їх і не змінюй production-контент. Відсутність таких варіантів — відома якісна межа, яку слід показати в звіті.

Перевірка правильності для особистого тренажера може виконуватися на клієнті. Це не захищена система іспиту; не додавай серверну антишахрайську платформу. Сервер зобов’язаний забезпечувати права доступу, цілісність переходів і надійне збереження.

## 8. React-архітектура

Межі відповідальності, а не обов’язковий шаблон папок:

- domain: типи, інваріанти, переходи, черга, нормалізація. Без React, DOM, Supabase, поточного часу і прихованої випадковості; час/seed приходять аргументами.
- application: координація дій, один pending command, retry, loading/conflict/auth lifecycle.
- data: repository Supabase, DTO mapping, runtime validation, класифікація помилок.
- ui: екран маршруту, картка знайомства, форма відповіді, feedback, підсумок, прогрес.
- integration: mount/unmount, навігація та доступ до поточного auth/client.

Не дублюй лічильники й відсотки в кількох незалежних state. Похідні значення обчислюй зі збережених фактів. Запити на зарахування викликай як наслідок явної дії, не через useEffect, що спостерігає за correctCount. Effects — для завантаження/підписок із cleanup; reducer залишається чистим. Увімкни StrictMode у розробці; не вимикай його для приховування повторних записів.

React володіє лише своїм контейнером. При виході з розділу коректно звільняй підписки. При зміні користувача скидай локальний стан та ігноруй старі відповіді запитів. Не створюй другий auth listener/client без потреби. Збережи стилі у межах модуля, щоб уникнути глобальних CSS-регресій.

Обробка помилок: error boundary для аварії компонента, окремі UI-стани для очікуваних мережевих/даних помилок. Невалідний збережений стан не перезаписуй початковим. Вихідні дані repository перевіряй під час виконання; TS сам цього не робить.

## 9. Дані та протокол запису

### 9.1. Мінімальна модель

Після перевірки схеми обери компактну модель, що покриває:

- рівень/сеанс: власник, kind (level/review), номер рівня де застосовний, статус, rules/schema version, пороги, revision, стан поточної вправи/черги, час початку/завершення;
- слова сеансу: порядок, word_id, snapshot, три лічильники, статус виключення;
- довготривалий стан слова в маршруті: факт завершення, last_practiced_at, ознака помилки останнього повторення;
- receipt операції: owner, session_id, operation_id, payload fingerprint/еквівалент, факт застосування й результуюча revision;
- явні answer variants, якщо немає придатного наявного сховища.

Реляційні ключі/власність/лічильники зберігай так, щоб їх можна було перевіряти. Компактний versioned JSONB допустимий для черги/feedback/snapshot. Не накопичуй усю історію натискань в одному необмеженому JSON. Не дублюй одну істину без атомарного оновлення. Документуй причини вибору та правила видалення.

Інваріанти: максимум один active рівень і один active review на користувача; слово не повторюється в одному сеансі; лічильники цілі й у межах порогів; completed можливий лише після завершення всіх доступних слів; номер рівня не дублюється; session word належить тому самому власнику. Простий FK на words.id сам по собі не перевіряє останню умову.

### 9.2. Операції та повтори

Один запис бізнес-дії має бути атомарним на сервері: лічильник, feedback, revision, завершення/прогрес слова і receipt не повинні оновлюватися незалежними HTTP-запитами. Реалізуй невеликий транзакційний RPC/наявний еквівалент. Це не привід додавати окремий серверний застосунок.

Команда містить operation_id, expected_revision, exercise_id, тип і обмежений payload. Owner визначається з auth.uid(), а не довіреного параметра клієнта. Для зміни рівня перевіряй допустимість дії, поточну вправу, власника, незмінні пороги та доступність слів. Не дозволяй клієнту без перевірки замінити довільним JSON весь прогрес.

Порядок виконання у транзакції: авторизація → потрібне блокування/узгодження конкурентних запитів → пошук receipt → перевірка revision та передумов → застосування → запис receipt → commit. Точну реалізацію узгодь із БД.

- Повтор того самого operation_id з тим самим payload не змінює прогрес вдруге, навіть якщо expected_revision вже стара. Перевірка receipt має передувати відхиленню повтору через revision.
- Той самий operation_id з іншим payload відхиляється.
- Якщо після першої операції вже були інші, replay не повинен відкотити UI до старого receipt: поверни ознаку застосованої операції та перечитай/поверни актуальний стан.
- Інша операція зі старою revision повертає conflict; клієнт перечитує актуальний стан і пояснює «Прогрес оновлено в іншій вкладці». Не зливай лічильники автоматично.
- Старт рівня також має захист від паралельних запитів через транзакцію, унікальність і блокування/еквівалент.

На клієнті один запис у польоті на сеанс. Retry повторює ту саму команду й operation_id. Після невідомого результату через timeout не створюй нову команду. Тимчасовий результат можна показати відразу, але підтверджений прогрес/наступна вправа доступні після ack. На помилці — «Не вдалося зберегти» й «Повторити», без тихого пропуску.

Після reload джерелом істини є сервер. Не потрібне збереження незаписаної offline-черги в цій версії. Документуй retention receipt: вони мають покривати строк допустимих повторів; у v1 автоматичне видалення receipt не потрібне. Не зберігай зайві сирі введені тексти у receipt/log, якщо достатньо типу результату та fingerprint.

### 9.3. Безпека і помилки

RLS і grants для кожної нової таблиці/функції. Перевір SELECT та можливі записи, підміну owner, чужі session_id/word_id та неавторизований доступ. Нові об’єкти не повинні змінювати права старих розділів.

Для RPC явно обери invoker/definer. Якщо definer потрібен для записів тільки через RPC: зафіксуй search_path, використовуй schema-qualified імена, перевіряй auth.uid()/ownership усередині, обмеж EXECUTE й прямі записи клієнта. Не вважай RLS автоматичним захистом усередині definer. Змінюй grants тільки нових об’єктів, не всього public schema.

Не додавай service_role у браузер. Розрізняй missing migration, permission denied, expired session, network, conflict і invalid data; не називай кожну помилку «міграція не застосована». Корисні технічні коди залишай у безпечній діагностиці без токенів і персональних відповідей.

## 10. Коротке повторення

Реалізуй після стабільного ядра. На головному екрані — окрема кнопка; перед новим рівнем — пропозиція, яку можна відкласти. Активний review можна продовжити пізніше, але одночасно в UI виконується лише один сеанс.

Початкове продуктове правило: доступні слова завершених рівнів, із останньої практики яких минуло щонайменше 24 години. Час — серверний UTC; це інтервал, не календарний «новий день». Параметр конфігурований, без заяв про науково оптимальний інтервал.

Бери до 5 слів: спочатку найстаріший last_practiced_at, при однаковому часі — слова з помилкою, потім стабільний id. Так слабкі слова не витісняють назавжди інші. Немає кандидатів — не блокуй рівні.

Кожне слово перевіряється один раз у кожному напрямку; помилкові/розкриті відповіді повертаються максимум на одну додаткову спробу в тому самому напрямку. Максимум 20 спроб для 5 слів. Ця межа замінює попередню нескінченну вимогу «до правильної відповіді». Після ліміту заверши review й покажи, що ще варто повторити.

Зберігай сеанс, факт практики й any_error в межах останнього review, включно з помилкою, виправленою на повторній спробі. Не збільшуй число опрацьованих нових слів і не переписуй завершені рівні. last_practiced_at оновлюй для слова після проходження обох напрямків (із їхніми запланованими повторами), щоб одне натискання не відкладало неперевірене слово на добу.

Це обмежене повторення з фіксованим інтервалом. Воно не замінює наявний SRS і не повинно змінювати його due_at/review_level/streak.

## 11. Метрики, доступність і продуктивність

Екран: поточний рівень, етап 1/3–3/3, лічильник поточного слова, режим, стан збереження, опрацьовані слова й кнопка продовження. Рівень з усіма виключеними словами не враховується як успішний.

Прогрес рівня = сума зарахованих переглядів і правильних відповідей / сума порогів невиключених слів. Наприкінці останнього feedback може бути 100%, але статус ще «Натисни Далі для завершення». При нульовому знаменнику — cancelled_empty, без NaN.

Загальний показник = кількість доступних зараз слів із завершеним маршрутом / кількість доступних зараз придатних слів. Додавання слів може зменшити відсоток; показуй також точне «N із M». Порожні/некоректні he/ua виключаються з кандидатів із видимою кількістю проблемних записів. Не обчислюй фіксовану загальну кількість рівнів, яка стає неправильною після додавання/видалення слів.

Клавіатура, label, видимий focus, aria-live результату, lang/dir для HE і UK, коректний порядок фокуса. Не вкладай інтерактивні кнопки в button-картку; обери семантично коректну структуру. Перевір 320/390/768 px і desktop, довгі слова/переклади, reduced motion. Якщо реальну мобільну клавіатуру не перевірено, не видавай desktop viewport-тест за таку перевірку.

Завантажуй React-модуль за потреби, якщо це узгоджується зі збирачем. Дані/приклади отримуй пакетно для потрібного сеансу; загальні метрики не повинні вимагати завантаження всіх прикладів. Зафіксуй розмір production assets і кількість запитів типового рівня; оптимізуй лише підтверджені проблеми. Не додавай віртуалізацію для п’яти карток.

## 13. Публікація і Definition of Done

Зміни БД — additive, сумісні зі старим frontend. Міграція перевірена на чистій тестовій БД і з наявними даними, якщо середовище доступне. Застосовану міграцію не переписуй — для виправлення створюй наступну. За відсутності середовища вкажи статус «SQL підготовлено, не виконано».

Порядок майбутнього релізу: перевірка тестового середовища → резервна копія/можливість відновлення БД → міграція → smoke SQL/auth → frontend → smoke навчання. Ці production-дії описати, не виконувати. Для відкату frontend використовувати попередню збірку/вимкнення нового розділу; не видаляти таблиці з накопиченим прогресом. Перевір кешування старого service worker, якщо є.

Готовність до production потребує реальної перевірки міграції, RLS/RPC і збереження. Якщо вони заблоковані, можеш завершити код і документацію, але познач результат як «локальна реалізація, очікує інтеграційної перевірки». Не оголошуй усе завершеним лише через зелений build.

Доставити в репозиторії: модуль, міграції, тести, коротке архітектурне рішення, інструкції запуску/застосування/відкату, результати A01–A18 (passed/failed/not run) і відомі обмеження контенту. Фінальний звіт: конкретні зміни, фактичні команди/результати, невиконані перевірки з причинами та наступні дії користувача. Не включай секрети.

## 14. Підсумок рев’ю попередньої редакції

Збережено: React + TypeScript, поступова інтеграція, п’ять слів, два режими, три етапи, окремий прогрес Supabase, повторення і відсутність автоматичного production deploy.

Виправлено: умовність вибору Vite до огляду репозиторію; поетапна доставка; snapshots після редагування; точний момент зарахування та завершення; строгий протокол replay/conflict; транзакційність; права RPC; Unicode-пастка й/ї; межі підтримки синонімів; обмежена тривалість review; правила відсотків; відмінність локальної готовності від production readiness.

Це рев’ю вимог, а не аудит поточного репозиторію: автор цього ТЗ бачив скриншот звіту, але не актуальний код на Mac користувача. Остаточні імена таблиць, типи, точки інтеграції та сумісність збірки визначає локальний Codex за реальним кодом.
