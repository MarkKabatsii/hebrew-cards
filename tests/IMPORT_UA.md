# Крок 3: валідація та імпорт слів

## Що виправлено

Одна функція `validateWord` перевіряє ручне додавання, JSON і текстовий імпорт. Поле івриту має містити івритські літери; арабські, латинські та кириличні літери, включно зі змішаним написанням, відхиляються. Нікуд, звичайна пунктуація та цифри дозволені. Приховані службові символи відхиляються. Обов’язкові поля мають бути непорожнім текстом, категорія та розділ — відповідати `taxonomy.js`.

Текст нормалізується до Unicode NFC, зайві пробіли прибираються. Нікуд зберігається: однакові літери з різними голосними можуть позначати різні слова. Перевірка формату не визначає правильність вимови чи перекладу.

Парсер підтримує JSON-масив, CSV, TSV, крапку з комою та вертикальну риску. Є автоматичний і ручний вибір роздільника. Поля з роздільником або переносом рядка беруться у подвійні лапки; внутрішні лапки подвоюються. Вбудовані лапки у звичайному полі (`נדל"ן`) теж підтримуються. Заголовки можна переставляти; невідомі колонки експорту, зокрема `id` і `user_id`, ігноруються. Імпорт не переносить власника чи прогрес з експортованих даних.

Помилки формату або валідації блокують запис усього списку. Перед перевіркою та кожною спробою імпорту перечитується актуальна БД; дублікати в ній і в самому списку пропускаються. Під час читання файлу та запитів поля й кнопки заблоковані. За помилки першого завантаження на сторінці імпорту є кнопка повтору.

Запис відбувається блоками по 200 карток. Якщо наступний блок не записався, попередні можуть залишитися в БД. Повідомлення показує лише кількість підтверджених додавань; текст зберігається для повтору. Повтор перечитає БД й пропустить збережені картки. Якщо відповідь сервера загубилася, непідтверджений блок також міг зберегтися; перечитування потрібне і в цьому випадку. Це не одна транзакція для всього списку.

Ручне додавання теж перевіряє актуальні дублікати та блокує повторне натискання. Після запису використовує повернену сервером картку: збій подальшого читання вже не маскує успішне додавання.

`data/words.json` синхронізовано з раніше виправленим словником: ті самі 416 початкових карток без ID, власників і прогресу. Приклади транскрипції в `data/words-example.txt` виправлено. Зміна цих файлів сама по собі не змінює існуючі записи Supabase.

## Автоматична перевірка

Із кореня проєкту:

```bash
node --test tests/progress.test.cjs tests/import.test.cjs
```

38 перевірок: 17 попереднього кроку та 21 цього кроку. Нові перевірки охоплюють абетки, Unicode, JSON, категорії, CSV із заголовками/лапками, усі 416 карток, дублікати, блокування форми, помилки читання, частковий запис і повтор імпорту. Використовуються підставні DOM та відповіді сервера; доступ до живої БД не потрібний.

## Ручна перевірка після публікації

1. На сторінці додавання вставити `אaני` у поле івриту: додавання має блокуватися. Іврит із нікудом має проходити перевірку.
2. На сторінці імпорту вибрати «Загальновживані слова → Займенники», завантажити `data/words-example.txt` і натиснути «Перевірити». Наявні слова мають рахуватися як дублікати; ця кнопка нічого не записує.
3. Додати один неправильний рядок до списку й натиснути «Імпортувати»: жоден рядок не повинен записатися.
4. Перевірити CSV із заголовком `he,tr,ua` та перекладом у лапках, що містить кому.
5. Після першого завантаження ввімкнути Offline в інструментах браузера й натиснути «Імпортувати». Текст має залишитися; після повернення мережі спробу можна повторити.

Переривання між блоками перевірене автоматично. Браузерні перевірки та імпорт у живий Supabase агентом не виконувалися. Новий SQL для цього кроку не потрібний: використовується унікальний індекс першого кроку. Перевірка абеток працює у застосунку; прямий запис через SQL чи API її не виконує.
