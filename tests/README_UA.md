# Крок 2: збереження прогресу

Запуск автоматичних перевірок зі кореня проєкту:

```bash
node --test tests/progress.test.cjs
```

Тести використовують справжні функції UI, Scheduler, Store, навчання та квізу з підставними DOM, таймерами й відповідями сервера. Додаткових пакетів не потрібно. 21 перевірка охоплює повторні натискання, повільний запис, помилки та повтор запису, завершення старого запиту/таймера після зміни сесії, відсутню картку, конфлікт прогресу між вкладками та повернення карток після настання терміну повторення.

## Поведінка після змін

- Під час збереження оцінки категорії та розділи тимчасово заблоковані. У навчанні блокування діє також протягом переходу до наступної картки.
- Кожна сесія має свій номер. Результат запиту або таймера від попередньої сесії не змінює нову чергу чи рахунок квізу.
- У навчанні за помилки картка залишається відкритою: оцінку можна натиснути повторно.
- У квізі відповідь показує правильність одразу, але лічильник і доступ до «Далі» оновлюються лише після підтвердження запису. За помилки доступна кнопка «Повторити збереження»; вона повторює запис того самого вибору.
- Store отримує оновлений рядок із сервера через `select(...).single()` і використовує саме його значення прогресу. Нуль змінених рядків не вважається успіхом.
- Запис умовний: ID, рівень, серія правильних відповідей, кількість помилок та попередній `last_reviewed_at` мають збігатися з прочитаними значеннями. Якщо інша вкладка змінила прогрес, старий запис не перезапише новий; користувач побачить повідомлення з проханням оновити сторінку.
- Порожній список показує найближчу дату повторення за місцевим часом браузера. Коли цей час настає, список автоматично перевіряється знову. Повернення у фонову вкладку теж запускає перевірку порожнього списку; поточна активна картка не змінюється. Використовуються вже завантажені дані, без додаткового запиту до БД.
- «1 день» означає 24 години від оцінювання. Дробові інтервали показуються точно: наприклад, `1,5 дн.` або `4,5 дн.`. Алгоритм розрахунку термінів не змінено.

Схема Supabase та алгоритм інтервалів у цьому кроці не змінюються. Повторний SQL не потрібний. Автоматичного злиття оцінок двох вкладок або фонової черги офлайн-запису немає. Якщо сервер прийняв запис, але відповідь загубилася в мережі, повтор зі старим станом покаже конфлікт замість повторного зарахування; потрібно оновити сторінку.

## Ручна перевірка після публікації

1. Відкрити головну сторінку, перевернути картку, натиснути оцінку. Під час запису й переходу повторні оцінки та перемикання розділів заблоковані. Після переходу кнопки знову доступні.
2. Пройти декілька питань квізу, включно з неправильною відповіддю. Після успішного запису рахунок збільшується один раз, а «Далі» відкриває наступне питання.
3. Після завантаження слів увімкнути Offline у браузерних інструментах розробника та відповісти у квізі. Має з'явитися помилка, рахунок не змінюється. Повернути мережу та натиснути «Повторити збереження»: відповідь зараховується один раз.
4. Аналогічно перевірити повтор оцінки на головній сторінці після помилки мережі.
5. Відкрити ту саму картку у двох вкладках до її оцінювання. Зберегти оцінку в першій, потім у другій. Друга вкладка має повідомити про застарілий стан; після оновлення вона повинна отримати актуальний прогрес.
6. Після завершення розділу перевірити дату найближчого повторення. Залишити сторінку відкритою до цього часу або повернутися у вкладку після нього: картки мають з’явитися автоматично. Для перевірки змін з іншого пристрою потрібно перезавантажити сторінку.

Ці браузерні та інтеграційні перевірки ще не виконувалися агентом із живим Supabase. Автоматичні перевірки не звертаються до БД й не змінюють картки.
